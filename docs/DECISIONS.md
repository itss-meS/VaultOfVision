# Decisions and deviations

> Edge-server material. This document describes the Raspberry Pi and Python backend track, which lives in the separate AgriEdge edge repository. It is kept here for reference; the mobile app in this repository does not use a server.

Precedence: white paper, then master prompt, then `Thought_for_51s.docx`, then `PlantAI_formatted.docx`.

1. **Optional `affected_area_pct` on `VisionResult`.** The advisory needs the affected area, and the client round-trips the vision result. Added as an optional nullable field to both the schema and the TypeScript type.
2. **`AdvisoryResponse` wrapper.** `advisory_v3` rejects unknown fields, so the dosage result, `case_id` and `source` travel beside it. `EngineClient.ask` therefore returns `AdvisoryResponse`, not a bare `Advisory`.
3. **Dosage arguments are rebuilt by code.** The model may emit a `tool_call`, but the orchestrator overwrites `crop`, `area_ha` and `severity` from trusted context and adds the disease label server-side. Missing area gives `area_missing`; missing table row gives `no_vetted_entry`. No number is ever invented.
4. **Severity thresholds 5, 15, 30, 50 percent are provisional.** They are configurable in YAML and need agronomist review.
5. **Vision result is client supplied on `/advisory`.** It is schema validated and the label must be in the configured class list. A tampering user only changes their own advice.
6. **Production configs fail closed.** `rpi5_hailo`, `rpi5_cpu` and `android` refuse to start while their real adapters are missing; there are no mock adapters in the product code. `configs/windows_dev.yaml` uses the real adapters with relaxed cookies and synthetic signed assets for local testing. Test doubles live only in `tests/fakes.py`.
7. **Banned list and dosage table must be supplied and signed.** `knowledge/` ships without them. Dev mode generates synthetic signed ones under `.dev/` (clearly labelled, not agronomic advice). The dev banned list contains "Endosulfan" and a placeholder only; the official list comes from the human.
8. **numpy pinned to 2.4.6** because 2.5.x needs Python 3.12 and Raspberry Pi OS Bookworm ships 3.11. Verified that all pins resolve to aarch64 wheels for 3.11.
9. **Login uses profile code plus PIN.** Typing a UUID is poor UX; QR pairing is planned for provisioning.
10. **Row-level security ADR.** SQLite has no RLS. Isolation is enforced by profile-scoped repository functions. Enable RLS on every table if Postgres or Supabase is introduced.
11. **SQLCipher** (`sqlcipher3-binary`, optional extra) is mandatory outside dev mode; the key is a 64-hex file in the key directory generated by provisioning.
12. **Browser voice input** uses the platform SpeechRecognition API, which may need network on some devices. Offline STT (whisper.cpp) arrives in Phase 4, so voice input is not yet guaranteed offline.
13. **Hindi and Marathi strings** were written without native review. Marathi is not an officially supported Llama 3.2 language, so quality must be measured.
14. **The UI has no mock engine.** The APK uses `NativeEngineClient`, which needs the Kotlin plugin from Phase 4, so the Phase 0 APK cannot analyse photos yet. The web UI talks to the real backend over HTTP.
15. **Two engines on purpose.** The Python core serves the backend and the Pi; a TypeScript port in `ui/web/src/engine/core/` serves the APK so the phone needs no server. Both follow the same flow and schemas. The TypeScript templates are generated from the Python text, and its validators are tested against the shared JSON schemas with Ajv. Changes to flow or schemas must be made in both.
16. **Hand-written validators in the app.** The CSP forbids eval, so no runtime JSON-schema compiler is used on the phone; Ajv is a test-only dependency.
17. **On-phone login enrolment.** On a fresh install the first profile id and PIN entered create the account (role farmer). Later logins verify the PIN (PBKDF2-SHA256, 210,000 iterations; 5 failures lock for 30 seconds). No TOTP on the phone. The session is in memory only.
18. **Severity stays empty without polygons.** A classifier gives no lesion area, so `severity_level` is null and no dosage total is computed until a segmentation model exists.
19. **Llama delivery.** The `.pte` (about 1.1 GB) is not in git or in the APK. It is a GitHub Release asset downloaded on first launch and verified by a signed hash.
20. **Training modes.** `train_all` supports one dataset, `separate` (one model per dataset) and `combined` (one model, prefixed class names). `--activate` is refused with `separate`.
21. **Advice is still tomato-only (open item).** The `crop` enum in `advisory_v3`, the prompt text, the retrieval filter, the dosage tool arguments and the unsupported-label rule assume tomato. Required change: derive crop and disease from the vision label, remove the enum in favour of a crop string validated against the loaded knowledge, make the healthy check match labels ending in "Healthy", keep dosage vetted-only per crop. Not implemented yet.
22. **Model licensing.** Llama 3.2 community licence and Ultralytics AGPL-3.0 both affect distribution; see `MODELS.md`.
